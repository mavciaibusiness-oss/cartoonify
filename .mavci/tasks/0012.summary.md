## Execution summary

This task enlarges the upload preview in the workbench's left panel from a 64 px square to a panel-wide, aspect-ratio-preserving letterboxed image capped at 32 vh (changed from the spec's 35 vh by the operator during the build). It removes the synthetic one-card "Varsayılan" group and makes Klasik Karikatür the first card of the first group, with a "Varsayılan" badge, both in the picker and the showcase. The showcase group headings lose their counts, and `landing.groupCount` is removed from both i18n dictionaries.

The initial build found that at 1280×624 the action buttons' bottom edge sat at 625 px (one pixel beyond the 624 px viewport), passing criterion 32 only via its ±1 px tolerance. At 375×667 the preview went from 341×233 to 341×213 and the button bottom remained at 650 px (visible). The fix was a one-line CSS change inside attempt 1, not a spec change. Both the main session's re-run of criterion 32 (`exit 0 in 1684 ms`) and the recorded verdict (`exit 0 in 1689 ms`) ran after the fix.

**The default card as a display property.** A new pure module `lib/style-display.ts` (34 lines) exports `displayGroups()` and `isDefaultStyle(id)`. The module imports only `lib/cartoon-styles.ts` (no aliases, no dependencies); it is loaded by Node in criterion 34, so the import carries an explicit `.ts` extension, with a `// @ts-expect-error TS5097` suppression on line 9 (line 3 is the comment explaining it). The spec did not change `lib/cartoon-styles.ts` (classic remains `coords: null`, outside the data grid). Both the picker and the showcase now render from `displayGroups()`, which places `DEFAULT_CARTOON_STYLE_ID` (classic) first in the first group. The badge is rendered by `style-card.tsx` and shown in the showcase by `style-showcase.tsx`, displaying the existing `form.defaultGroup` string ("Varsayılan" in Turkish, "Default" in English).

**Showcase headings without counts.** The `span.showcase-count` and the `.showcase-count` CSS rule are removed. `landing.groupCount` is removed from both `lib/i18n/tr.ts` and `lib/i18n/en.ts` (grep confirms 0 remaining uses). ## System findings

One finding was filed by the main session on 2026-09-30 at 09:09:36Z and amended at 09:13:24Z (both UTC), queued for decision and not applied:

**Finding 59 — The architect's prototype worktree reached the project's real node_modules through a Windows Junction, and deleting the worktree followed the junction and deleted the packages.** The architect built a prototype in a git worktree of `f3a9faa`, using `mklink //J` to create a junction from the worktree's `node_modules` to the project's real `C:\Projelerim\cartoonify\node_modules`. The worktree was then removed, most likely by the operator's `git worktree remove --force` (addendum). The deletion went through the junction and stopped partway. The project's node_modules was left with 22 top-level entries, all alphabetically from "next" onward; `.bin` and everything before "next" were gone. For scale, package-lock.json lists 105 node_modules entries. The main session restored the tree with `npm ci` (63 entries). Later in the same session, the main session's own `git worktree remove --force` of a second worktree failed with "Filename too long" when that worktree's junction had already been removed with `rmdir`, so the project's node_modules was unaffected.

The plugin has no guidance on prototype worktrees or junctions, and the risk guard does not examine junction creation. The spec pattern (task 0011 §11.1, repeated for task 0012) is not a plugin feature. The finding's direction (from the operator's account): a prototype worktree runs its own `npm ci`. If a junction is used anyway, it must be removed with `rmdir <link>` before the worktree is removed, because `git worktree remove` follows the junction. This applies to the operator's cleanup as well as to agents'.

The addendum to finding 59 (filed at 09:13:24Z) records the operator's account. The deletion of the architect's prototype worktree at about 08:52 was most likely the operator's `git worktree remove --force`, a command suggested by a chat assistant. It stopped partway with "Filename too long", which matches the partial loss. The same error ended the main session's later `git worktree remove --force` of the second worktree, whose junction the architect had already removed. The addendum states that whether `git worktree remove` follows junctions in general was not independently tested.
