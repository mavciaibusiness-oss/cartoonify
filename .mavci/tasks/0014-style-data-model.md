# Task 0014 — Style data model: an explicit category, two merges, legacy ids redirected

- **Task id:** 0014
- **Project:** cartoonify
- **Phase at writing:** plan
- **Depends on:** `f1a84c5` (0013's `data/style-catalog-draft.json` is the source of every category)
- **Paid calls:** none. No image is generated. The API criterion (43) talks to a
  local stub that stands in for the provider, and nothing leaves the machine.
- **Two build steps:** step A is the builder's. Step B is the main session's,
  with operator authority, because `scripts/check-styles.mjs` is outside the
  builder's scope. This is 0013's route A (§8).

---

## 1. What this task is

The operator's request, in four parts:

1. **An explicit `category` field** on every style in `lib/cartoon-styles.ts`.
   The values are the 12 categories of `data/style-catalog-draft.json`, and
   the category names go into the TR and EN dictionaries. The spec decides
   whether `coords` is retired or kept as a side field (§3.2).
2. **Two merges:** `cel-frame` → `classic` and `combed-paint` → `thick-paint`.
   - The two merged styles leave the picker and the showcase, which leaves
     **29 active styles**.
   - The API redirects the old ids to the style each one merged into. No
     other API behaviour changes.
   - 0012 criterion 22 froze `app/api`. That freeze is renewed here with this
     one reason (§3.5).
   - §3.6 says what happens to the merged styles' preview files.
3. **`scripts/check-styles.mjs` checks `category`.** The builder cannot write
   `scripts/*.mjs`, so the main session writes it with operator authority as a
   separate step B (§8).
4. **The site looks the same.** The picker and the showcase keep today's group
   layout. Splitting 29 styles across 12 categories would create one-card
   rows. `category` is data only, and 0015 uses it as a filter.

**Out of scope:** new images, the filter, search, and any layout change (§12).

## 3. Decisions this spec makes explicitly

### 3.1 `category` is stored, not derived

- **The type.** `export type StyleCategory` is the 12 ids.
- **The list.** `export const STYLE_CATEGORIES`, in 0013 §4.1 order:
  `cartoon, line, drawing, paint, print, paper, textile, sculpt, caricature,
  graphic, era, surface`. It must be written as an array literal introduced by
  `= [`, because criterion 42 edits that form.
- **On each record.** Every `STYLE_SOURCE` record carries a property written
  literally as `category: '<id>',`, placed after `description`. Criterion 42
  edits that exact form.
- **On the output.** `CartoonStyle` gains `readonly category: StyleCategory`,
  and `CARTOON_STYLES` copies it.
- **The values** equal `data/style-catalog-draft.json`'s `category` for each id
  (criterion 35). The draft is the approved plan. It is read by the acceptance
  criteria only. The application and `check-styles.mjs` never import it.
- **Why stored.** The 12 categories are medium families, not regions of the
  coordinate grid. For example, `modelled-caricature` is `sculpt`, while its
  coordinates put it in `kesme`. No `deriveCategory(coords)` exists that
  reproduces the approved plan.

### 3.2 `coords` stays, as a side field. It is not retired.

**Decision:** `coords` and `asserts` stay on every record, byte for byte as
today. `category` sits beside them and does not replace them.

**Why:**
1. **Today's layout depends on it.** `group` is `deriveGroup(coords)`, and the
   operator requires the layout to stay (§1.4). Retiring `coords` means either
   storing `group` by hand or changing the layout. The first reopens exactly
   the drift that `deriveGroup` exists to prevent. The second is out of scope.
2. **The prompts depend on it.** `closingFor(coords)` picks the closing
   sentence that is sent upstream. Retiring `coords` would need a stored
   closing on each record, so this task would touch what is sent to the paid
   provider for all 29 styles. Criterion 36 freezes every prompt byte for byte.
3. **The checker depends on it.** `check-styles.mjs`'s separation rule and its
   assertion column are the only guard against two styles in a group looking
   alike. `category` has no equivalent rule yet.
4. **The file itself says so.** The comment in `lib/cartoon-styles.ts` says
   "DO NOT MOVE coords/asserts OUT OF THIS FILE", and gives the reason.

**When it can be revisited:** in the generation task that rewrites the 79
prompts (0013 §6), or once 0015's filter has replaced the groups on screen.
Until both have happened, `coords` does real work.

### 3.3 Category names go into both dictionaries

- **Where.** `lib/i18n/tr.ts` and `lib/i18n/en.ts` gain a top-level key
  `styleCategories` with exactly the 12 ids as keys.
- **The text** is 0013 §4.1's TR and EN columns, verbatim. Criterion 41 reads
  that table and compares.
- **Typing.** In `tr.ts` it is typed so that a missing category is a compile
  error: `satisfies Record<StyleCategory, string>`, or equivalent, with an
  `import type` only. `tr.ts` stays free of runtime imports.
- **Nothing renders them in 0014** (criterion 41).

### 3.4 The merge: the ids leave, and a redirect map remains

- **In `lib/cartoon-styles.ts`:**
  - The `cel-frame` and `combed-paint` records are **removed** from
    `STYLE_SOURCE`. 29 remain, in today's order.
  - `CartoonStyleId`, `isCartoonStyleId` and `getCartoonStyle` then cover
    active styles only. `isCartoonStyleId('cel-frame')` becomes `false`.
  - A new map is written literally as
    `export const MERGED_STYLE_IDS = { 'cel-frame': 'classic', 'combed-paint': 'thick-paint' }`,
    with `as const` or `satisfies` allowed. Criterion 42 edits the
    `'cel-frame': 'classic'` and `'combed-paint': 'thick-paint'` pairs.
  - `export type MergedStyleId = keyof typeof MERGED_STYLE_IDS`.
- **A new resolver,** `export function resolveCartoonStyleId(value: unknown): CartoonStyleId | null`:
  - it returns an active id unchanged;
  - it returns a merged id's target;
  - it returns `null` for anything else, including non-strings, wrong case,
    padded strings and `Object.prototype` names such as `__proto__`,
    `constructor` and `toString`. Use own-property lookups (criterion 37).
- **In the route** (`app/api/cartoonify/route.ts`), only two places change:
  - The import from `'@/lib/cartoon-styles'` swaps `isCartoonStyleId` for
    `resolveCartoonStyleId`.
  - In step 6, from the `// 6.` comment line up to the line
    `const style = getCartoonStyle(styleId)`, the membership test becomes a
    resolution: `resolveCartoonStyleId(styleField)`, then `null` →
    `errorResponse('INVALID_STYLE', 400)`, then the resolved id →
    `styleId`.
  - The `form.getAll('style')` cap stays before resolution, unchanged. Two
    `style` fields are still 400, even when one of them is a legacy id.
  - Keep both boundary lines. Criterion 38 compares everything outside them
    byte for byte with `HEAD`.
- **What does not change:** status codes, error codes, error text, the
  response shape, the ordering of the checks (file, then type, then style,
  then key, then upstream), the upstream parameters, and the prompt of every
  active style. Criterion 38 holds all of them in the source, because
  nothing outside step 6 may change. Criterion 43 exercises the status codes,
  the error code, the prompts and the redirect against a running server.

## 4. Build steps

**Step A: the builder** (all paths in scope, §8).
1. `lib/cartoon-styles.ts`:
   - add `StyleCategory` and `STYLE_CATEGORIES`;
   - add `category` to 29 records with the draft's value, and to
     `CartoonStyle` and `CARTOON_STYLES`;
   - remove the `cel-frame` and `combed-paint` records;
   - add `MERGED_STYLE_IDS`, `MergedStyleId` and `resolveCartoonStyleId`.
   - Change no `name`, `description`, `coords`, `asserts` or `body`.
2. `app/api/cartoonify/route.ts`: the two edits of §3.4, nothing else.
3. `lib/i18n/styles.en.ts`: remove the two entries. Updating the "31" in its
   header comment is optional.
4. `lib/i18n/tr.ts` and `lib/i18n/en.ts`: add `styleCategories` (§3.3) and
   change `meta.workshopDescription` (§3.7).
5. `lib/style-previews.ts`: remove the two ids.
6. `lib/style-web-manifest.json`: remove the two entries, and keep the
   `JSON.stringify(x, null, 2) + '\n'` form.
7. Delete the four files of §3.6 with plain `rm <path>` (no `-r`, no `-f`) or
   `git rm <path>`.
8. `lib/gallery.ts` and `components/gallery.tsx`: G1 (§3.8).
9. Run `npm run check` and `npm run build`. Both must pass, and the **old**
   `check-styles.mjs` passes on the new data. The builder is **not** expected
   to make criterion 42 green: that is step B.

**Step B: the main session, with operator authority** (0013 route A).
After step A and before `/mavci-core:verify`, the main session edits
`scripts/check-styles.mjs` so that it also fails when:
1. `STYLE_CATEGORIES` is not 12 unique `[a-z0-9-]` ids;
2. any style lacks `category`, or its category is not in `STYLE_CATEGORIES`;
3. any `MERGED_STYLE_IDS` key is an active style id or is not a slug, or any
   value is not an active style id.

It prints a per-category count on its summary line. It keeps every existing
check. It does not read `data/`, because the plan file is not an application
input.

It is written against the step-A data and run with `npm run check:styles`.
Criterion 42 proves each failure mode on a scratch copy. Then the task goes
to verify.

## 9. Why each part is safe

- **Reversible:** yes, fully. There is no schema and no migration. The deleted
  files are in git history, and `git revert` restores everything. No ADR is
  needed.
- **Trust boundary:** the style allow-list is still the control. A caller can
  still only name an id, never prompt text. The redirect map is a fixed
  constant, so it cannot be used to widen what reaches the provider.
- **Tenancy:** none (single-tenant, no database).
