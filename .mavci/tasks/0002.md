# Task 0002 — Bound the upstream call to the route's own ceiling, discriminate an unreachable provider from a size-degraded rejection, and stop the error message claiming a cause

- **Task id:** 0002
- **Project:** cartoonify
- **Phase written in:** plan
- **Standards packs in force:** `nextjs-app-router`, `legal-tr-kvkk`
- **Risk tier:** standard
- **Sources:** `.mavci/lessons/pending-system-change.md` finding 11, the addendum to finding 11, finding 12
- **Related decisions:** `.mavci/decisions/0002-missing-api-key-is-a-product-state.md`, `.mavci/decisions/0004-the-small-body-probe-is-server-side-evidence.md`

---

## 1. What is being changed

One file: `app/api/cartoonify/route.ts`. Three fixes, all inside the existing
handler and its catch block.

1. **The OpenAI client gets a timeout and a retry budget derived from
   `maxDuration`.** Today the client is constructed with SDK defaults —
   `timeout: 600000`, `maxRetries: 2`, verified in `node_modules/openai` at
   4.104.0 — which is up to thirty minutes of willingness inside a route that
   declares a sixty-second ceiling. On Vercel the platform kills the function
   first, the catch block never runs, and the user meets a platform error page
   instead of the designed error state. Finding 11 part 1.
2. **An `APIConnectionError` triggers a small-body probe, logged server-side.**
   A large multipart upload can be cut mid-request by a provider that has already
   computed a rejection, so a transport error is not evidence of a transport
   problem. A small-body request to the same base URL answers what the multipart
   request structurally cannot: did *any* HTTP response arrive? Finding 12.
3. **The unreachable case gets its own error code and a message that claims
   nothing about cause or remedy.** Addendum to finding 11.

**Nothing else.** No new dependency, no new route, no change to the UI, no change
to `lib/env.ts`, no change to `maxDuration` itself, no rate limiter, no test
runner.

## 2. The three decisions this spec makes explicitly

### 2.1 Tenancy

Zero tables touched, zero created. `stack.db` is `"none"`; there is no tenant
column to add and no RLS policy to write, and `supabase-multitenant-rls` is not
in `standards.packs` and must not be reintroduced. Every visitor is anonymous and
identical. This task adds no per-visitor state, no cookie, no session, and stores
nothing — the probe's result goes to the server log and nowhere else.

### 2.2 Trust boundary

Unchanged from task 0001 and re-asserted here because this task adds a **second**
OpenAI client:

| Runs where | What | Sees `OPENAI_API_KEY`? |
|---|---|---|
| Server | `app/api/cartoonify/route.ts` — the request client **and the new probe client** | Yes, via `getEnv()`, at request time only |
| Server | `lib/env.ts` — the only file permitted to read `process.env` | Yes, it is the source |
| Browser | everything under `components/`, `app/page.tsx`, `app/layout.tsx` | **Never** |

The probe client is constructed **inside** the failure path at request time, with
`getEnv()`, exactly like the request client. It must not be hoisted to module
scope, must not be memoised across requests, and must not appear in any module the
client bundle can reach.

The probe's outcome is written to `console.error` and **never to the response
body**. See §2.4 and decision 0004.

### 2.3 Reversibility

Fully reversible. One file, no migration, no schema, no external account change,
no infrastructure change, no dependency change. `git revert` restores the current
tree exactly. Nothing in this task spends upstream credit — see §6.0.

### 2.4 The decision that is not obvious: the probe never changes what the user is told

Every `APIConnectionError` returns `UPSTREAM_UNREACHABLE` with the same fixed
message, **whether the probe reaches the provider or not**. The probe's finding
lives in the log.

The alternative — return `UPSTREAM_ERROR` when the probe gets an HTTP response,
because that implies the provider refused rather than vanished — was rejected.
It infers a cause from a correlation, in the exact place where finding 12 says
inference is unsafe, and it makes the user-facing surface depend on a second
network call that may itself fail for unrelated reasons. Recorded as decision
0004, with the endpoint choice.

## 3. Measured facts that constrain the fix

These were measured on the running dev server (Next 14.2.35, `next dev`,
`http://localhost:3000`) against the **unchanged** route, and they are the reason
the timeout is not a free choice.

| Observation | Value |
|---|---|
| `POST /api/cartoonify`, no body | 400 `NO_FILE` in **0.34 s** |
| `POST /api/cartoonify`, 67-byte 1×1 PNG, real upstream, real key | 200 in **35.06 s** (`POST /api/cartoonify 200 in 35056ms`) |
| SDK defaults, openai 4.104.0 | `timeout = 600000`, `maxRetries = 2` |
| Route ceiling | `export const maxDuration = 60` |

**The success path takes 35 seconds.** Any budget at or under ~35 s aborts
requests that work today. The derived timeout must therefore sit *above* 35 s and
*below* 60 s, and the whole wall clock — request attempt plus probe — must still
fit inside the ceiling. That is a narrow window and §5.1 pins it.

Two further facts, both of which shape what a criterion is allowed to depend on:

- **The upstream key currently has quota.** Finding 11/12's
  `429 insufficient_quota` does not reproduce today; it was yesterday's account
  state. No criterion in this spec depends on the provider misbehaving on cue.
  Every fault path is provoked locally, by pointing the SDK's base URL at a
  process under our control.
- **A live generation costs real credit.** One success observation already
  exists, recorded above. No criterion here performs a second one.

## 5. Contracts

### 5.1 The derived budget

At module scope in `app/api/cartoonify/route.ts`, immediately after the existing
segment config, these three declarations, with these exact right-hand sides
(the comment above them may be worded freely):

```ts
export const dynamic = 'force-dynamic'
export const runtime = 'nodejs'
export const maxDuration = 60

const UPSTREAM_TIMEOUT_MS = Math.floor(maxDuration * 1000 * 0.75)
const PROBE_TIMEOUT_MS = Math.floor(maxDuration * 1000 * 0.1)
const UPSTREAM_MAX_RETRIES = 0
```

**Derived, not written twice.** The point of the formula is that `maxDuration` and
the transport budget cannot drift apart again; a literal `45_000` would be a second
number maintained by a different concern, which is the defect finding 11 describes.
No numeric millisecond literal may be passed to `timeout:`.

**What it evaluates to at `maxDuration = 60`:**

| Constant | Value | Why that value is the right one |
|---|---|---|
| `UPSTREAM_TIMEOUT_MS` | **45 000 ms** | Above the 35.06 s measured success, so it does not abort requests that work today. Below 60 000, so the SDK always gives up before the platform does and the designed catch block is what the user meets. |
| `PROBE_TIMEOUT_MS` | **6 000 ms** | The probe is diagnostics; it must never be the reason the ceiling is breached. |
| `UPSTREAM_MAX_RETRIES` | **0** | Forced, not chosen. With one retry the worst case is 45 + 45 + 6 = 96 s, past the ceiling. Retrying a reset multipart upload costs the full timeout again and, in the case actually observed, could never have succeeded. |

Worst case wall clock: **45 + 6 = 51 s < 60 s**, with 9 s of headroom for form
parsing and response assembly.

`maxDuration` stays at 60. Changing it invalidates every number in this table and
is out of scope.

### 5.2 The error codes

`ErrorCode` gains exactly one member and `ERROR_MESSAGES` gains exactly one entry.
`typecheck` enforces that the record stays exhaustive, so a missing message is a
build failure rather than an `undefined` in a response body.

| Code | Status | Message (Turkish, fixed constant) | When |
|---|---|---|---|
| `UPSTREAM_UNREACHABLE` | 502 | `Karikatür servisine ulaşılamadı. Sorun geçici olabilir; bir süre sonra tekrar deneyebilirsiniz.` | The SDK threw `APIConnectionError` (which includes `APIConnectionTimeoutError`) — **no HTTP response arrived** |
| `UPSTREAM_ERROR` | 502 | unchanged: `Karikatür oluşturulurken bir sorun oluştu. Lütfen tekrar deneyin.` | Anything else the try block throws, and the empty-result case |

The new message is the **revised** wording from the addendum to finding 11, and it
is exact to the byte. What it does and does not do:

- It says what is known — the service could not be reached.
- "Sorun geçici **olabilir**" — *may be* temporary, not *is*.
- No instruction to check anything. The rejected draft said
  `Bağlantınızı kontrol edip tekrar deneyin`, which sends a user to debug a
  network that is working, in the one case actually observed. That phrase is
  banned from the file by criterion 12.
- No implication that a retry will succeed. An unreachable provider may be
  permanently, account-level unreachable.

**502 for both**, deliberately. The status is not the discriminator; `code` is.
A distinct status would be a second claim about cause, and it would let a
criterion pass on the status line without ever reading the body.

`UPSTREAM_ERROR`'s existing message is **not** rewritten by this task. It is
asserted by task 0001's criteria and changing it is out of scope — see §8.

### 5.3 The catch block

```ts
} catch (unknownError) {
  // Logged server-side for operators; never forwarded to the response body.
  console.error('cartoonify: upstream call failed', unknownError)

  if (unknownError instanceof OpenAI.APIConnectionError) {
    await logSmallBodyProbe()
    return errorResponse('UPSTREAM_UNREACHABLE', 502)
  }

  return errorResponse('UPSTREAM_ERROR', 502)
}
```

`OpenAI.APIConnectionError` is a static on the default export (verified at
4.104.0) and `APIConnectionTimeoutError extends APIConnectionError`, so a timeout
takes this branch too. That is correct: a timeout is also "no response arrived".

This is an `instanceof` check, not a heuristic on message text. A `catch` that
inspects `err.message` for `ECONNRESET` fails this spec.

### 5.4 The probe

A module-scope `async function`, placed **last in the file**, after `POST` (so
criterion 14 can assert on everything following its declaration), called only from
the branch above, that **cannot throw** and **returns nothing**:

```ts
async function logSmallBodyProbe(): Promise<void> {
  try {
    const probeClient = new OpenAI({
      apiKey: getEnv().OPENAI_API_KEY,
      timeout: PROBE_TIMEOUT_MS,
      maxRetries: 0,
    })
    await probeClient.models.list()
    console.error('cartoonify: upstream probe result=reached status=200')
  } catch (probeError) {
    if (probeError instanceof OpenAI.APIConnectionError) {
      console.error('cartoonify: upstream probe result=unreachable', probeError)
    } else {
      const status = probeError instanceof OpenAI.APIError ? probeError.status : 'unknown'
      console.error('cartoonify: upstream probe result=reached status=' + String(status), probeError)
    }
  }
}
```

Four things about this are load-bearing:

1. **`result=reached` on any HTTP response, including 401, 429 and 400.** The
   question the probe answers is not "is the provider healthy" but "did a small
   body get an answer where a large one did not". An `APIError` *is* an answer.
   Only `APIConnectionError` is `result=unreachable`.
2. **`GET /v1/models`, not the endpoint the feature uses.** Smallest available
   body, no generation, no credit spent, and it cannot succeed expensively.
   Finding 12's own recommendation is the smallest-body endpoint available;
   its example (`/v1/images/generations`) is a paid endpoint that would generate
   an unused image and bill the operator every time the probe ran on a healthy
   account. Decision 0004 records this.
3. **The markers are structured ASCII**: `result=reached` and
   `result=unreachable`. They are what criteria 9, 10 and 15 grep for, and they
   are stable under any locale or console encoding.
4. **It swallows everything.** A probe that throws would replace the designed 502
   with an unhandled error — the diagnostic destroying the thing it was added to
   diagnose.

### 6.0 No criterion in this task contacts the real provider

Every fault path is provoked by pointing the SDK's base URL at a local process.
Total upstream spend for a full verification run: **zero**. The fixture is the
undecodable PNG from task 0001 — nothing decodes it, because the only thing that
would is the real provider, which is never contacted.

### 6.1 Fixtures and the fault-injection sink (written outside the repository)

```bash
T="${TMPDIR:-/tmp}/cartoonify-0002"; mkdir -p "$T"

# Valid PNG magic bytes + 1 KiB of zeros. Not a decodable image; nothing decodes it.
node -e "const fs=require('fs'),h=Buffer.from([0x89,0x50,0x4e,0x47,0x0d,0x0a,0x1a,0x0a]);fs.writeFileSync(process.argv[1],Buffer.concat([h,Buffer.alloc(1024)]))" "$T/px.png"

cat > "$T/sink.js" <<'EOF'
// Fault-injection stand-in for api.openai.com. Listens on 127.0.0.1 only.
// Logs nothing and stores nothing: it must never write out what it receives.
const http = require('http')
const MODE = process.env.MODE
http.createServer((req, res) => {
  req.resume()                                   // drain, never inspect
  const isModels = req.method === 'GET' && req.url.indexOf('/v1/models') === 0
  if (MODE === 'degraded' && isModels) {         // small body gets a clean answer
    res.writeHead(200, { 'content-type': 'application/json' })
    res.end('{"object":"list","data":[]}')
  } else if (MODE === 'degraded') {              // large body cut mid-request (finding 12)
    setTimeout(() => req.socket.destroy(), 50)
  } else if (MODE === 'refusing') {              // provider answers and refuses
    res.writeHead(400, { 'content-type': 'application/json' })
    res.end('{"error":{"message":"bad request","type":"invalid_request_error"}}')
  }                                              // MODE=hang: accept, never answer
}).listen(4599, '127.0.0.1')
EOF
```

Port **4598** is used for the `refused` case and nothing is ever started on it.
Port **4599** is the sink.

### 6.2 Server modes

The dev server is restarted with fault-injection environment for criteria 8–11
and 15, then restarted clean. Two `next dev` processes must not share `.next`, and
`next build` must not run while one is up, so the run order in §6.3 is part of the
spec, not a suggestion.

```bash
# Git Bash, repository root. The shell environment wins over .env.local:
# @next/env does not overwrite variables that are already set.
MODE=<mode> node "$T/sink.js" &                 # omit entirely for mode `refused`
OPENAI_API_KEY=probe-key-not-a-real-credential \
OPENAI_BASE_URL=http://127.0.0.1:<4598|4599>/v1 \
  npm run dev > "$T/dev.log" 2>&1 &
```

| Mode | Base URL | Sink | What the route meets |
|---|---|---|---|
| `refused` | `http://127.0.0.1:4598/v1` | none started | Connection refused on both calls — a genuinely unreachable provider |
| `degraded` | `http://127.0.0.1:4599/v1` | `MODE=degraded` | Multipart POST cut mid-request, small `GET /v1/models` answered 200 — finding 12 reproduced exactly |
| `hang` | `http://127.0.0.1:4599/v1` | `MODE=hang` | Nothing ever answers — the slow-upstream case that hits `maxDuration` on Vercel today |
| `refusing` | `http://127.0.0.1:4599/v1` | `MODE=refusing` | A clean HTTP 400 — the provider answered and refused |

The dummy key is set explicitly so the real credential is never sent to the sink.
The sink listens on loopback only and writes nothing.

### 6.2a The harness was verified before this spec was written

Findings 11 and 12 both close with "name the broken build the assertion catches,
and confirm the assertion fails against it first". The behavioural criteria here
depend on five assumptions about the SDK, every one of which was executed against
`openai` 4.104.0 in this repository's `node_modules` on 2026-09-05, with local
sockets only and no contact with the real provider:

| Assumption criteria 8–11 and 15 rest on | Measured result |
|---|---|
| A refused port produces `APIConnectionError` | `APIConnectionError`, `instanceof` true |
| `OPENAI_BASE_URL` redirects a client constructed with **no** explicit `baseURL` | `client.baseURL === http://127.0.0.1:4599/v1` — so the harness needs no product-code change |
| `degraded` mode: `GET /v1/models` is answered | 200, JSON parsed |
| `degraded` mode: the multipart `POST` cut mid-request | `APIConnectionError` — `result=reached` is provokable |
| `hang` mode: the client aborts at its own timeout | `APIConnectionTimeoutError`, `instanceof APIConnectionError` true, aborted at 1507 ms against a 1500 ms timeout |
| `refusing` mode: HTTP 400 | `BadRequestError`, `instanceof APIConnectionError` **false**, `status === 400` — criterion 15 discriminates |

The last row is the important one: it is the measurement that makes criterion 15
able to fail. Without it, a blanket `catch` that called everything unreachable
would pass criteria 8 through 11 and nothing would notice.

## 8. Out of scope, deliberately

- **`UPSTREAM_ERROR`'s message is not rewritten.** It still ends
  `Lütfen tekrar deneyin`, which is an instruction to retry, and by the reasoning
  in the addendum to finding 11 that is worth revisiting. But it is asserted by
  task 0001's criteria, the addendum's revision is explicitly about
  `UPSTREAM_UNREACHABLE`, and changing a message task 0001 verified is a separate
  decision with a separate approval. Criterion 12 pins it unchanged so the
  question stays open rather than being quietly closed. Recorded in
  `suggested_next`.
- **`maxDuration` is not raised.** 60 s is the ceiling this route declares and
  the Hobby-plan maximum for the Node runtime. Raising it changes every number in
  §5.1 and is a platform decision, not a code one.
- **No live generation is re-verified.** The 35.06 s success on 2026-09-05 is the
  observation of record; §5.1's 45 s budget is chosen to sit above it, and
  criterion 7 enforces that arithmetic without spending credit. A criterion
  requiring a fresh live success would cost money on every verification run and
  would be `not_run` whenever the account state changed — which under 0.1.33
  makes the whole verdict `incomplete`.
- **Reporting the mid-upload connection cut upstream** (finding 12 consequence 4)
  is an operator action against a third-party account, not a code change.
- **No rate limiter, retry queue, circuit breaker, metric, test runner or new
  dependency.**

## 9. Escalate rather than guess

- If `npm run typecheck` or `npm run build` cannot pass without touching a file in
  the do-not-touch list, stop and escalate. Do not widen the change.
- If `OPENAI_BASE_URL` turns out not to redirect the SDK in this environment, the
  fault-injection harness collapses and criteria 8–11 and 15 become unrunnable.
  Stop and escalate rather than substituting inspection for the behavioural
  criteria — a spec whose fault paths are only inspected is the failure mode
  finding 11 was filed about.
- If the derived budget cannot satisfy all three inequalities in criterion 7 —
  for instance because a measured success time moves above 45 s — that is a
  product decision about `maxDuration` and the plan tier, and it is an
  escalation, not a number to adjust quietly.
- Never read, move or edit `.env.local`. It is `never_read_by_agents` in the
  manifest, and no criterion here requires its contents.
