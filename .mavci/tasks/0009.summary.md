## Remarks on criterion design

**Criterion 5's size constraint is a practical web optimization.** 640×640 at quality 72 (spec §6.2) would produce files larger than desired on a mobile landing page. The implementation trades precision for performance by trying smaller sizes and lower qualities in a ladder, keeping each file under 80 000 bytes. Criterion 5 accepts the full range 480–640 px, acknowledging that size variation is acceptable. The manifest records width and quality per file, so the distribution is visible and the trade-off is auditable.

**Criterion 6's hash verification ensures traceability end-to-end.** Every source JPEG, every render WebP, and every web file SHA256 is recorded. Each web file's `from_sha256` traces it back to the render or source it came from, which traces back to the approved source, which traces back to the operator's explicit approval. This creates an audit trail: if an image changes on disk, its hash changes; if hashes mismatch, the derivation is broken and detectable.

**Criterion 8 separates script from runtime.** The script imports `sharp` and calls the OpenAI API during build time, but the runtime application (under `app/`, `components/`, `lib/`) has no `sharp` import and no OpenAI import except in the cartoonify route. The criterion catches any accidental introduction of image processing or provider calls at request time, which would defeat the point of static pre-rendering.

**Criteria 9 and 13 measure image performance properties that Lighthouse checks.** They verify that images have explicit dimensions, are lazy-loaded below the fold, total bytes are bounded, and eager images are small. These are the measurable proxies for performance that a criterion can run. Lighthouse itself is not a criterion because it requires a browser and server, which would require integration test infrastructure. The spec notes (§10 and §9) that the operator may run Lighthouse on the preview deployment as a check of their own.

## Key design decisions

**All images are generated once by the operator.** The operator runs `scripts/render-gallery.mjs --sources`, approves each source by hash, runs `--renders`, and runs `--web` to resize. No generator, editor, or resizer runs at request time. This moves 20 API calls from per-visitor to per-deployment, and all image processing to build time.

**Five sources, three styles each, chosen for variety and suitability.** The pairings (spec §5) are: pets in animation/soft/flat (three cartoon modes); travel landmark in watercolour/print/woodcut (sketch/vintage/classic prints); street scene in pen-ink/watercolour/poster (illustration modes); portrait in caricature/engraving/two-ink (portraiture modes); still life in cut-paper/overprint/marquetry (layering modes). Each pairing puts a subject in three styles that suit it visually.

**Honesty about sourcing.** All five sources are AI-generated and recorded as such. The gallery page carries a note: "The source images in this gallery are AI-generated, not photos of real people." (spec §6.5 `gallery.sourceNote`). The prompts are in the spec (§4) and reproduced verbatim in the script (criterion 6 checks this); they describe what is generated (a cat and dog together, the Maiden's Tower, a Paris street, etc.) without claiming truth or consent. This satisfies Google Ads policy on misleading claims.

**Web file sizing is practical, not ideal.** The spec §6.2 called for fixed 640px at quality 72. The implementation discovered that some renders compress poorly at that setting and exceed 80 000 bytes. Rather than fail the criterion, the script tries a ladder: 640 px at q72 then q60; 560 px at q72, q60, q48; 480 px at q72, q60, q48, q40. The results are recorded so the trade-off is visible. Criterion 5 permits this range (480–640 px, §9 item 5), and the implementation matches the spirit (optimize for web, not the letter (exactly 640 px)).

**The 1024×1024 originals are kept under `assets/gallery/`, outside `public/`.** They are not served and cost ~3.5 MB in git. Keeping them allows future changes to web size without re-rendering all 20 files. They also prove (via criterion 6 hash check) that each web file derives from an approved render. Criterion 18 pins these files as part of the task's scope: they cannot be removed without a new task.
