## 1. What this task is, and what it is careful not to be

The operator's request, verbatim in substance:

> Monica-style landing page. On the left a large before/after (the existing
> `public/hero/before.jpg` pair), on the right the upload box. The KVKK notice
> stays in front of the upload box. Turkish by default, English under `/en` with
> the same structure. Below, a gallery: 5 new source images (cat/dog, Kız Kulesi,
> a Paris street, an adult man's portrait, a still life) × 3 styles that suit
> each = 15 renders. Static under `public/gallery/`, made by a one-time script
> under `scripts/`, no API call at runtime. No invented statistics.

Three pieces of work, in this order:

1. **Layout.** The hero becomes two columns on wide screens: the existing pair
   (`/hero/before.jpg` and `/styles/classic.webp`) on the left, the upload column
   on the right. The upload column holds the KVKK notice and then the upload
   control, in that DOM order. On narrow screens it stacks in DOM order: pair,
   notice, upload.
2. **Gallery assets.** One script, `scripts/render-gallery.mjs`, generates five
   source images, stops for the operator to look at them, then renders fifteen
   edits and writes resized WebP copies to `public/gallery/`. It runs once, by the
   operator, on their machine. Nothing it does happens at request time.
3. **Gallery section.** A server component, `components/gallery.tsx`, renders the
   five rows below the hero on `/` and `/en`: each source beside its three
   renders, each render labelled with its style's existing localised name.

**What it is careful not to be.** Listed explicitly because each one is a thing a
landing page redesign drifts into:

- **No invented numbers.** No user count, star rating, review count, conversion
  count, "trusted by", percentage or any other figure that is not a fact about the
  product. The only digits the rendered landing may show are the ones it shows
  today: the upload step number, the maximum upload size and the style count per
  group (criterion 12). This is Google Ads policy (misleading claims), not taste.
- **No sign-in, no watermark, no credits.** Those are task 0010. This task adds
  no route, no page, no table, no API and no client state.
- **The 31 styles and their previews are not touched.** `lib/cartoon-styles.ts`,
  `lib/style-previews.ts`, `lib/preview-manifest.json`, `public/styles/`,
  `public/hero/` and `scripts/render-previews.mjs` are frozen by criterion 18.
  The hero pair is reused as it is on disk.
- **No prompt is written or tuned.** Every render uses a style's existing prompt
  through `getCartoonStyle`, exactly as a visitor's request does.
- **The KVKK notice's text and component are not edited.** Only its position
  inside the new layout is specified, and that position keeps it before the file
  input.

## 3. Three decisions this spec makes explicitly

### 3.1 Tenancy

None. No auth, no store, no session, no table. The gallery is a set of static
files and a build-time manifest about twenty provider calls.

### 3.2 Trust boundary

**Nothing new reaches the client except static images and dictionary strings.**
`components/gallery.tsx` is a server component with no `'use client'` and no
`fetch` (criterion 8). The only module under `app/`, `components/` or `lib/` that
imports `openai` stays `app/api/cartoonify/route.ts`, and nothing there imports
`sharp` (criterion 8).

**The key.** The gallery script reads `OPENAI_API_KEY` through `lib/env.ts` only,
exactly as `render-previews.mjs` does. `lib/gallery.ts` is pure data and safe to
bundle. The manifest records hashes, prompts, usage and cost, never a secret or a
request id.

**Where a visitor's photograph goes does not change.** The KVKK notice is
untouched and still precedes every file input (criterion 11).

**Spend is a control.** `SPEND_CEILING_USD = 1.00` in the script; it stops before
any call that would cross it. Criterion 7 checks the record.

### 3.3 Reversibility

The code is reversible by reverting the commit. **The spend is not:** twenty paid
calls, about 0.40 USD (§7). The gallery assets stay in git history after a
revert. No migration, no ADR needed.

## 4. The five sources: where they come from

**All five are generated with `gpt-image-2.5-sunburst` (the model the route
uses), from prompts written in the script and recorded in the manifest. None is a
downloaded photograph, CC0 or otherwise.**

Why not CC0: every "free photo" source that would supply these five has a
provenance question this task cannot settle mechanically. Unsplash and Pexels
use their own licences, not CC0, and exclude some uses; Wikimedia Commons
licences vary per file and must be read one at a time; a street scene or a
portrait carries identifiable people who never signed a model release; a Paris
street carries shop signs and trademarks. A generated image with a recorded
prompt has one provenance: OpenAI's terms assign the output to the caller. For a
page that will run Google Ads, one clean answer beats five that need checking.

**Honesty about it.** The gallery carries one line, in both languages, saying the
source images are AI-generated (`gallery.sourceNote`, criterion 14). The hero's
`alt` text already says so for the hero portrait. Presenting generated images as
customer photos would itself be a misleading claim.

The prompts, carried verbatim by the script (criterion 6 checks the recorded
prompt is in the script):

## 6. The design

### 6.1 `lib/gallery.ts`

```ts
import type { CartoonStyleId } from './cartoon-styles'

export type GallerySourceId = 'pet' | 'maiden-tower' | 'paris-street' | 'man-portrait' | 'still-life'
export type GalleryEntry = { readonly id: GallerySourceId; readonly styles: readonly [CartoonStyleId, CartoonStyleId, CartoonStyleId] }
export const GALLERY: readonly GalleryEntry[] = [ /* §5, in order */ ]
```

Type-only import, relative path, no `@/`: criteria load it with plain Node.
Paths are derived, never stored: `/gallery/<id>/source.webp` and
`/gallery/<id>/<style>.webp`.

### 6.2 `scripts/render-gallery.mjs`

Follows `render-previews.mjs`: imports `IMAGE_MODEL`, `IMAGE_QUALITY`,
`IMAGE_SIZE`, `uploadFilename`, `sniffImageType` from `lib/image-constraints.ts`,
`getCartoonStyle` from `lib/cartoon-styles.ts`, `getEnv` from `lib/env.ts`,
`GALLERY` from `lib/gallery.ts`; `maxRetries: 0`; manifest rewritten after every
call. No probe: task 0008's probe already confirmed this model accepts exactly
these parameters, and the calls here have the same shape.

| Mode | Paid | What it does |
|---|---|---|
| `--sources [--only <id>] [--force]` | yes, 5 | `images.generate` per §4 prompt → `assets/gallery/<id>/source.jpg`. Then STOP |
| `--approve <id> <hex prefix>` | no | records `approved: { sha256_prefix, at }` if the prefix matches the file on disk |
| `--renders [--only <id>]` | yes, 15 | refuses any source without approval; `images.edit` of the source with the style's prompt, output WebP at compression 80 → `assets/gallery/<id>/<style>.webp` (1024×1024); skips renders already done from this source |
| `--web` | no | `sharp` resizes each source and render to **640×640 WebP, quality 72** → `public/gallery/…`; records `from_sha256` and `sha256` per file |

The spend check runs before every paid call. Manifest: `lib/gallery-manifest.json`,
with `model`, `quality`, `size`, `ceiling_usd`, `rates`, `sources`, `renders`,
`web_files`, `discarded`, `last_error`. The field names are the ones criterion 6
reads.

**Why keep the 1024 originals in `assets/gallery/`.** They are outside `public/`,
so never served, and about 3.5 MB in git. Without them, changing the web size
later means paying for fifteen renders again. They also let criterion 6 prove
each web file derives from an approved render.

**Why `sharp` as a devDependency.** The provider returns 1024×1024 at minimum; a
gallery card is shown at about 200–300 CSS px. Serving 1024 files would put about
4 MB of images on the landing. `next/image` would resize at request time on
Vercel, which the request rules out in spirit (runtime work per image) and which
criterion 13 forbids. `sharp` runs only in the script; criterion 8 forbids a
runtime import and criterion 18 allows it only under `devDependencies`.

### 6.3 Layout: `components/landing.tsx`

```
<main class="landing">
  <section class="landing-hero">            badge, h1, lede (unchanged)
    <div class="landing-stage">             wide screens: grid, pair left, upload right
      <div class="hero-pair">…</div>        existing two figures, unchanged, eager
      <div class="landing-upload">
        <KvkkNotice/>                       notice first…
        <UploadControl/>                    …then the file input
      </div>
    </div>
  </section>
  <section class="landing-gallery">         <Gallery locale/>
  <section class="group-intro">…            unchanged
  <section class="how-it-works">…           unchanged
</main>
```

- `.landing-stage` becomes a two-column grid inside the existing
  `@media (min-width: 900px)` block, roughly `1.25fr 1fr`, left heavier: "large
  before/after". The pair inside keeps its own two columns.
- **No CSS reorders anything**: no `order`, and no `grid-row`, `grid-area` or
  `*-reverse` on any landing rule (criterion 11). The visual order and the DOM
  order are the same thing, so "the notice comes first" holds for a screen reader,
  a keyboard and a narrow screen alike.
- The upload column is `position: sticky` on wide screens, optional; the builder
  decides.

### 6.4 The gallery: `components/gallery.tsx`

Server component. A heading, a one-line lede, the AI-source note, then five rows.
Each row: the source figure (caption: "Kaynak" / "Source") and three render
figures, each captioned with the style's name via `styleText(style, locale)`.
Every `<img>` has `loading="lazy"`, `decoding="async"`, `width="640"`,
`height="640"` and a localised `alt`. The grid uses `repeat(4, 1fr)` on wide
screens and `repeat(2, 1fr)` on narrow ones; **no numeric `minmax`** (criterion
17: task 0004's criterion 11 reads the first numeric `minmax` in the file and
expects `.style-grid`).

### 6.5 Strings

New keys under `landing` and a new `gallery` group in `lib/i18n/tr.ts` and
`lib/i18n/en.ts`, in parity (criterion 15). No visible string in a component
(criterion 16). Proposed Turkish, for the operator to amend at approval:

|---|---|---|

| `gallery.lede` | Her satırda bir kaynak görsel ve ona yakışan üç Cartoonify stili. | Each row shows one source image and three Cartoonify styles that suit it. |
| `gallery.sourceNote` | Galerideki kaynak görseller yapay zekâ ile üretilmiştir; gerçek kişi veya müşteri fotoğrafı değildir. | The source images in this gallery are AI-generated; they are not photos of real people or customers. |
